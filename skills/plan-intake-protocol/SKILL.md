# Plan Intake Protocol

用户提出新计划、目标或想法时的标准化 intake 流程。核心原则：**先检验动机框架，再进入执行；读取用户已有思考，不让用户重复；识别状态切换信号，不拖延执行。**

## 触发场景

以下用户表达应激活此流程：
- "我要做 xxx""我的计划是 xxx""接下来我要 xxx"
- "你忘了 xxx""你没按 xxx 来"（框架纠正）
- "我在 obsidian/文件里写了 xxx"（异步思考文件）
- "够了""就这样""实现吧""推进吧""一个个实现吧"（执行切换信号）
- "我们做了吗""这个做了吗""xx 完成了吗"（任务追踪）

## 工作流程

### 第一步：框架优先，而非从零收集

当用户提出新计划时，**先检查用户是否已有建立的价值评估框架**（如认知操作系统、个人决策清单、之前对话中确立的评估问题等）。

- 如果存在已有框架：先用该框架检验计划，而不是提出通用的信息收集问题
- 如果不确定是否有框架：简要搜索记忆库或询问"你之前建立的 xx 框架，需要先用它来检验这个计划吗？"
- 只有在用户确认没有框架或需要新建时，才从零开始设计评估问题

**常见错误**：默认进入"产品经理式"信息收集，问一堆标准问题（目标、范围、预算、时间线），而用户已经建立了更深层的行为框架。

### 第二步：接受框架纠正，不辩解

如果用户指出"你忘了 xxx""你没按 xxx 来""这些都不是最重要的问题"：

1. 立即承认偏离（"你说得对"）
2. 停止当前路径
3. 回到用户指定的框架
4. **不要解释**为什么之前问了那些问题

用户纠正本身就是 intake 流程的一部分，不是失败。

### 第三步：推断需加验证句

当基于用户的认知体系对其动机或状态做推断时，结尾必须附加：

> "如果这个推断是错的，你直接告诉我。"

给用户明确的否定通道，避免助手陷入"过度解读—反驳—再解读"的循环。

### 第四步：尊重"活在当下"型动机

如果用户表达以下信号：
- "觉得有趣"
- "活在当下"
- "没有过多想法"
- "只是想试试"

**不要追问"真正的动机是什么"，不要强行赋予深层意义。** 接受"兴趣驱动"作为充分理由，转而讨论：
- 这件事的时间预算是多少？
- 它会不会挤占其他主线的时间？
- 把它放进系统的哪个位置？

### 第五步：主线单一原则

用户倾向于一次只推进一条主线。当用户确认当前主线后：
- 不要同时展开多个并行任务
- 不要追问"那你另一个计划怎么办"
- 如果有关联事项，记录为"待处理"，等当前主线完成后再启动

### 第六步：读取异步思考文件

当用户说"我在 xx 里写了""xx 里有我的思考"：

1. 立即使用 read 工具读取该文件
2. 基于文件内容回应
3. **不要让用户重复文件里已有的内容**
4. 如果需要澄清，只针对文件中未明确的部分追问

### 第七步：识别执行切换信号

以下表达意味着用户要求**停止分析，进入执行**：
- "够了"
- "就这样"
- "实现吧"
- "推进吧"
- "一个个实现吧"
- "看看 xx"（配合上下文的执行意图）

收到这些信号后：
1. 停止追问、解释、分析
2. 立即列出待执行项
3. 询问执行顺序（如果有多项）
4. 开始执行

### 第八步：任务追踪回应

当用户问"我们做了吗""这个做了吗""xx 完成了吗"：

1. 准确汇报完成/未完成状态
2. 引用具体的完成位置（文件路径、skill 段落、模板条目）
3. 如果部分完成，说明哪些做了、哪些还没做
4. 不要模糊回答"应该做了"

## 禁忌

- **不要**在已有框架的情况下从零开始设计评估问题
- **不要**对用户的框架纠正做辩解或解释
- **不要**强行赋予用户行为深层意义
- **不要**让用户重复文件里已有的内容
- **不要**在执行信号出现后仍继续分析
- **不要**同时推进多条主线
