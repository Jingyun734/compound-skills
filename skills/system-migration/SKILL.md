# 系统迁移与清理工作流

当用户要求用新组件替代旧组件时，按照以下步骤执行。

## 第一步：逐层排查所有涉及的组件

不要只处理用户提到的那一层。排查以下所有层面：

| 层面 | 检查项 | 示例 |
|------|--------|------|
| 技能层 | `.hanako/skills/` 和 `learned-skills/` 中是否有功能重叠的技能 | cognitive-os 和 companion-v2 都在处理元认知 |
| cron 层 | 定时任务中是否有功能重叠或已被替代的任务 | 旧的晚间巡检 cron 和新的晚间简报 cron |
| 文件层 | Obsidian 目录中是否有旧系统遗留的文件目录 | _agent/ 迁到 助手/认知伙伴/ |
| 配置层 | 用户的 pinned.md、ishiki.md 中是否有重复定义 | 身份锚点同时出现在 pinned 和 companion 技能中 |

## 第二步：列出完整对比清单按格式输出

```
## 当前状态（旧）
### 技能层
- [技能名] — 功能描述（原因：与新系统重叠）
### cron 层
- [cron 标签] — 触发时间，功能描述（原因：被替代）
### 文件层
- [路径] — 内容描述（建议操作：删除/归档/迁移）
### 配置层
- [配置项] — 当前值（建议操作：删除/更新）

## 目标状态（新）
### 技能层
- [技能名] — 功能描述
### cron 层
- [cron 标签] — 触发时间，功能描述
### 文件层
- [路径] — 内容描述
### 配置层
- [配置项] — 值
```

## 第三步：确认后执行

只有在用户明确同意（如「嗯」「都执行了」「可以」）后才执行删除操作。

执行顺序：
1. 先删除/归档旧组件
2. 再创建新组件
3. 最后更新所有引用（wikilink、cron 提示词路径等）
4. git commit

## 第四步：验证无孤儿

迁移后检查：
- 旧目录是否已删除（如有文件需先迁移或归档）
- 新组件的路径引用是否正确
- 是否有任何文件/配置引用了已删除的路径
- 用户是否还有未处理的历史文件残留

## 常见陷阱

- 只加不减：最常见的错误。用户说「换成这个」，必须删除旧组件，不能只创建新的
- 遗漏覆盖层：用户提到 cron，但同一功能可能在技能层和文件层也有遗留
- 预设用户会用模板：除非用户明确说，否则不要假设用户会填写结构化内容
- 文档来源必须是官方文档：写使用说明时基于官方文档，不基于对话内容
- 物理分组优于逻辑分组：用户要求文档分组时是建子文件夹，不是只在文件里加链接
